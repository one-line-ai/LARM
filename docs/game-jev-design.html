LARM 게임이론·Jev 결정 설계

LARM의 결정론 규칙 위에 Jev의 보정된 확률을 얹고, 그 확률을 게임이론 전략의 입력으로 써서 "언제 검사하고, 무엇을 알리고, 무엇을 먼저 보고, 얼마나 두고 볼지"를 근거 있게 정하는 설계다. 판정은 규칙이, 확률은 Jev가, 전략은 게임이, 결정은 사람이 맡는다.

원칙. Jev는 위험 판정을 바꾸지 않고 순서·타이밍·기본값만 바꾼다. 게임 전략은 Jev 확률의 함수이며, Jev가 없거나 보정이 나빠지면 전략은 규칙만으로 후퇴한다. 모든 확률은 "참고 확률 · Jev v버전"으로 표시하고 나중의 실제 결과와 대조해 보정을 검증한다.

2. Jev 질문 계약

한 번의 호출에 질문 7개를 병렬로 넣고 확률과 값을 함께 받는다. 호출 시점은 점검 저장 직후, 알림 결정 직전, 앱을 열 때 세 곳이며 입력 요약값이 같으면 캐시를 쓴다. 응답 예산은 200ms이고 넘기면 규칙만으로 진행한다.

3. 게임별 설계

G1 검사 게임: 언제 다시 확인할까

참가자
LARM(검사 시점 선택) 대 변경자(설정을 바꾸는 쪽. 사용자 자신일 수도, 악성 프로젝트나 주입된 지시일 수도 있음)
보수
검사 비용 c(CPU·배터리), 미감지 지연에 따른 손실 L·(지연 시간). 변경자는 검사 사이 틈이 길수록 유리
Jev 입력
Q5의 q(60분 내 변경 확률), Q3의 s(사용자 변경 확률). 위험 가중 r = 1 − s
결정 규칙
T = clamp(T_min=10분, T_max=60분, T_base=30분 / (1 + k·q·r)), 실제 간격 = T × U(0.7, 1.3)
LARM 동작
30분 고정 대조를 이 간격으로 바꾼다. 무작위 곱은 검사 시점 예측을 막는 혼합 전략이다. 파일 폴링 순서도 매번 섞는다
후퇴 규칙
Jev 없음 또는 응답 지연: T = 30분 × U(0.7, 1.3)
검증 지표
변경 시각에서 재점검까지의 지연 p95, 하루 대조 횟수, 유휴 CPU 1% 이하 유지(N05)

G2 늑대소년 게임: 알릴까 말까

참가자
LARM(알림 보냄·안 보냄) 대 사용자(열어 봄·무시). 반복 게임이며 무시가 쌓이면 진짜 위험도 묻힌다
보수
알림 가치 = 조치 필요 확률 × 반응 확률 × 위험 크기 − 방해 비용
Jev 입력
Q1의 a, Q2의 b
결정 규칙
V = a·b·L(위험도) − C_interrupt ; 보냄 ⇔ V > θ ; θ는 사용자 선택(보수·보통·적극), L(높음)=3, L(중간)=1
LARM 동작
V가 문턱 아래면 알림 대신 앱 배지만 유지하고, 문턱을 넘으면 기존 24시간 묶음 규칙 안에서 보낸다. 새 높은 위험과 감시가 끊긴 구간은 V와 무관하게 항상 보낸다(요건 F24)
후퇴 규칙
Jev 없음: 높음은 보내고 중간은 묶음. 지금 동작과 같음
검증 지표
알림 반응률, 놓친 높은 위험 0건, 하루 알림 수

G3 신뢰 반복 게임: 기준 상태를 권할까

참가자
사용자 대 각 외부 도구 연결(MCP)·프로젝트. 기준 상태 지정은 협력, 기준 이후 변경은 이탈로 본다(팃포탯)
보수
검토 없이 지정하면 위험을 숨기고, 지정하지 않으면 미검토 항목이 쌓여 주의가 분산된다
Jev 입력
Q3의 s
결정 규칙
권장 ⇔ s ≥ 0.8 ∧ 열린 높은 위험 = 0 ∧ 변경이 모두 사용자 작업 세션 안에서 발생
LARM 동작
바뀐 설정 화면에 "기준 상태로 지정 권장 (참고 확률 s)"를 표시한다. 지정은 사용자만 한다. 노드 상세에 검토 이력(검토 횟수, 마지막 변경 후 경과, 변경 빈도)을 표시하되 단일 점수는 만들지 않는다
후퇴 규칙
권장 표시 없음
검증 지표
권장 수용률, 기준 지정까지 걸린 시간, 권장 뒤 30일 내 같은 대상에서 높은 위험 발생 0건

G4 회피 진화 게임: 판단 보류를 어떤 순서로 볼까

참가자
규칙 작성자 대 회피자(인코딩·간접 실행·셸 래퍼). 서로의 수에 맞춰 진화한다
보수
규칙 쪽은 최악의 회피 집합에서 탐지율을 최대화(최소최대), 회피 쪽은 판단 보류에 머무르는 것이 목표
Jev 입력
Q4의 e
결정 규칙
검토 큐 정렬 = e 내림차순 ; 분기마다 e 상위 유형을 레드팀 fixture로 승격 ; 규칙 갱신은 fixture 전체에서 최소 탐지율을 올리는 방향
LARM 동작
판단 보류 기록을 자동으로 위험 확정하지 않는다. 사용자가 "회피 맞음·아님"으로 표시한 결과를 저장해 Q4 보정과 fixture 작성에 쓴다
후퇴 규칙
시간순 정렬
검증 지표
사후 확인된 회피 비율, fixture 수, 독립 검증 challenge set 탐지율

G5 약속 게임: 예외 기한을 얼마로 둘까

참가자
지금의 사용자 대 미래의 사용자. 기한은 미래의 나를 묶는 약속 장치다
보수
짧으면 재검토 부담, 길면 위험이 잊힌다. 연장이 반복되면 예외가 사실상 영구가 된다
Jev 입력
Q6의 d(권장 기한), p_renew(연장 확률)
결정 규칙
기본 기한 = d ; p_renew ≥ 0.6이면 기본 기한을 한 단계 줄이고(30→14→7) 사유 재작성 요구 ; 2회 연장부터 무조건 사유 재작성
LARM 동작
예외 입력란의 기본값과 안내 문구만 바꾼다. 최대 30일, 기한 필수라는 요건 F21은 그대로
후퇴 규칙
기본 7일
검증 지표
연장 횟수 분포, 만료 후 실제 조치율

G6 정보 가치: 무엇을 먼저 확인할까

성격
게임이 아니라 결정 이론. 확인 비용 대비 판단이 바뀔 기대값이 큰 항목을 앞에 둔다
Jev 입력
Q1의 a, Q7의 v
결정 규칙
오늘 확인할 항목 순서 = (높음 우선) → a·L 내림차순 → v 내림차순 → 오래된 순
LARM 동작
개요의 "오늘 확인할 항목"과 확인 못 한 항목 화면 정렬에 적용하고 각 항목에 "확인하면 알 수 있는 것" 한 줄을 붙인다
후퇴 규칙
높음 → 오래된 순(지금 동작)

G7 동조 방지 게임: Jev 자체를 누가 검증하나

참가자
개발자(Jev 층을 만드는 쪽) 대 독립 검증자. 둘이 같은 편이 되면 검증이 무너진다
보수
검증자의 보수는 "합의"가 아니라 "적발"에 걸려 있어야 한다. challenge set은 개발자가 보지 못한다
결정 규칙
브라이어 점수 B = 평균 (p − 결과)² ; B가 4주 이동 평균으로 0.25(동전 던지기)보다 나쁘거나 신뢰도 곡선 편차가 0.15를 넘으면 Jev 층 자동 끔 + 개요에 사유 표시
LARM 동작
질문별로 확률과 나중의 실제 결과(조치했는가, 해결됐는가, 열어 봤는가, 회피로 확인됐는가)를 로컬에 기록하고 모델 카드(브라이어, 신뢰도 곡선 10구간, 표본 수, 모델 버전)를 보고서 jev.json에 넣는다
검증
독립 검증(N10) 항목에 "Jev 보정 검증"을 추가한다. RYNTA의 ARI·AVI 분리 원칙과 같다

5. 화면과 보고서

  • 확률은 항상 "참고 확률 · Jev v버전" 칩으로, 규칙 판정 배지와 다른 모양으로 표시한다. 칩을 누르면 입력 필드와 결정 규칙(위 공식)을 보여 준다.
  • 설정 화면에 "Jev 결정 층 사용" 스위치(로컬 실행이면 기본 켜기, 원격이면 기본 끄기), 알림 문턱 3단계, 대조 간격 범위, "전송되는 상태 미리보기"(연결 등록과 같은 확인 흐름)를 둔다.
  • 개요에 "결정 근거" 줄을 추가한다. 예: "다음 대조 22분 뒤 (변경 확률 0.18) · 중간 위험 2건은 알림 대신 배지 (반응 확률 0.31)".
  • 보고서에 jev.json(추정·결과·모델 카드)과 strategy.json(게임 결정 이력)을 추가한다. 형식은 larm-evidence/1.2로 올린다.

F17 결정론 규칙판정 경로에 Jev를 넣지 않는다. Jev가 꺼져도 판정은 동일
F42·F43 제외Jev와 게임 층 어디에도 허용·차단 결정이 없다
N02 비밀정보 비저장Jev 입력은 보고서와 같은 마스킹 상태만 쓴다. 새 필드가 생기면 canary 시험에 추가
N04 오프라인로컬 실행이 기본. 원격 API는 사용자 동의와 전송 내용 미리보기 뒤에만, 실패 시 규칙만으로 동작
N10 독립 검증보정 검증(브라이어·신뢰도 곡선)을 검증 항목에 추가하고 challenge set을 개발자에게 숨긴다
N13 자원 상한호출당 200ms, 하루 호출 수 상한, 캐시. jev_call 표로 실측
F22 단일 점수 금지확률은 질문별로만 표시하고 합산 점수를 만들지 않는다

7. 단계별 도입

0단계 · 그림자 (2주)

Jev 어댑터와 로컬 스텁, 질문 7개 호출과 결과 기록만. 동작은 바꾸지 않음. 성공 기준: 호출 실패율 1% 미만, 200ms 이내, 결과 기록 누락 0

1단계 · 정렬과 알림

G6 정렬, G2 알림 게이트. 성공 기준: 놓친 높은 위험 0, 알림 반응률 상승

2단계 · 간격과 기한

G1 무작위 대조 간격, G5 예외 기본 기한. 성공 기준: 감지 지연 p95 개선, 유휴 CPU 1% 유지

3단계 · 신뢰와 회피

G3 기준 상태 권장, G4 판단 보류 큐와 fixture 승격. 성공 기준: 권장 수용률, fixture 10종 이상

4단계 · 검증과 자동 끔

G7 모델 카드, 브라이어 감시, 자동 끔, 독립 검증 항목. 성공 기준: 독립 검증 통과

8. 위험과 대응

  • 과신: 보정이 나쁜 확률로 전략이 틀어질 수 있다. 0단계 그림자 기간에 보정을 먼저 재고, 운영 중에는 G7의 자동 끔이 막는다.
  • 사용자 신뢰: 확률이 "왜"를 말하지 않으면 무시된다. 칩마다 입력 필드와 공식을 열어 보여 준다.
  • 데이터 부족: 개인 사용자의 결과 표본은 적다. 초기에는 규칙 우선·Jev 보조로 두고 표본 수가 질문당 30건을 넘기 전에는 전략 변화 폭을 절반으로 제한한다.
  • 프라이버시: 입력 스키마를 고정하고 필드 추가는 검토를 거친다. 원격 호출이면 전송 미리보기를 강제한다.

9. 시작에 필요한 것

  1. Jev 호출 방식: 로컬 실행인지 API인지, Swift에서 부르는 방법(SDK, 로컬 HTTP, CLI).
  2. 입력·출력 스키마 예시 하나. 위 2절의 개념 계약을 실제 형식에 맞춘다.
  3. 응답 시간 목표. 수십 ms면 알림 결정 경로에 동기적으로, 아니면 비동기로 순서만 갱신한다.

이 셋이 확정되면 0단계(어댑터·스텁·결과 기록)를 바로 구현한다.

10. 플레이어를 사용자와 에이전트로 본 정리

에이전트(Claude Code 같은 AI 코딩 도구)는 악의가 없어도 "일을 빨리 끝내는 것"이 목표라 넓은 권한을 원하고 지름길을 택하며, 주입된 지시에 조종당하면 그 목표가 바뀐다. 사용자는 일은 끝내되 위험과 방해를 줄이려 한다. 두 목표가 완전히 같지 않은 것이 게임의 출발점이다. LARM은 플레이어가 아니라 심판이다. 무엇을 기록하고 무엇을 보여 주며 어떤 기본값을 둘지 정해 게임의 정보와 보수를 바꾼다. Jev는 심판이 쓰는 확률 추정기다. 조종당한 에이전트는 별도 플레이어가 아니라 에이전트의 "유형"으로 다룬다.

10.1 게임 다섯 개

게임사용자의 선택에이전트의 선택문제Jev가 주는 확률LARM의 개입
1. 권한 위임 (주인·대리인)허용 범위(allow·ask·deny, 실행 전 확인 생략 여부)주어진 범위 안에서 어떤 명령을 쓸지사용자는 방해가 싫어 범위를 넓히고 에이전트는 넓은 범위를 다 씀(도덕적 해이)이 프로젝트에서 넓은 범위가 실제로 필요할 확률, 좁히면 확인 요청이 늘어날 확률R01·R02 발견 사항에 "좁혀도 되는 규칙"과 예상 확인 횟수를 함께 표시. 좁힐지는 사용자
2. 신호행동을 보고 계속 맡길지, 살펴볼지행동(파일 읽기, 명령 실행)이 곧 신호사용자는 에이전트가 정상인지 조종당했는지 볼 수 없고 행동만 봄행동 순서로 본 "조종당한 세션"일 확률(Q4)활동 기록이 신호를 판독 가능하게 만듦. 확률이 높은 세션을 먼저 보여 주되 판정은 사람
3. 반복 신뢰세션마다 신뢰(권한·예외)를 얼마나 줄지신뢰를 지킬지(안전한 변경) 어길지(위험한 설정 변경)기억이 없으면 어긴 뒤에도 다음 세션에 같은 신뢰를 줌이 에이전트·프로젝트가 다음 세션에 위험한 변경을 할 확률에이전트·프로젝트별 이력을 남겨 팃포탯이 가능하게 함. 기준 상태 권장(G3)이 여기 속함
4. 검사언제 설정을 다시 확인할지언제 설정(훅·MCP·허용 규칙)을 바꿀지확인 시점이 예측되면 그 사이에 바꿀 수 있음다음 변경까지의 시간, 60분 내 변경 확률(Q5)무작위 대조 간격(G1). 작업 중에는 촘촘히, 유휴에는 드물게
5. 주의 배분알림에 반응할지 무시할지얼마나 많은 사건을 만들지(에이전트는 신경 쓰지 않음)에이전트는 사건을 무한히 만들고 사용자 주의는 유한함조치 필요 확률(Q1), 반응 확률(Q2)알림 게이트(G2)와 정렬(G6). 같은 안전을 더 적은 방해로

두 플레이어 모두에게 적용되는 약속 장치가 하나 더 있다. 사용자는 확인 요청이 귀찮아지면 "전부 허용"으로 기우는데(승인 피로), Jev가 그 확률을 높게 보면 LARM은 기본값을 더 좁게 제안하고 예외 기한을 짧게 둔다(G5). 에이전트 쪽 약속은 훅 등록 자체다. 등록된 뒤에는 행동이 기록된다는 사실이 에이전트에게 전달되므로 기록만으로도 행동이 바뀐다.

10.2 정성적 효과

관점효과
정보 비대칭 해소에이전트의 행동이 기록되어 사용자가 "정상인지 조종당했는지"를 행동에서 읽을 수 있음. 신호 게임에서 분리 균형이 생기는 조건
위임의 정밀도허용 범위를 "귀찮음"이 아니라 "실제 필요 확률"로 정함. 넓은 허용을 줄이면서 확인 요청은 크게 늘리지 않음
기억 있는 신뢰세션이 끝나도 이력이 남아 다음 위임에 반영됨. 에이전트별·프로젝트별로 신뢰가 달라짐
예측 불가능한 검사설정 변경이 검사 사이 틈을 노릴 수 없음. 에이전트가 만든 설정 드리프트를 빨리 잡음
주의의 보존알림이 사용자의 반응 가능성까지 고려하므로 알림 하나의 무게가 유지됨
막지 않고 바꾸기LARM은 차단하지 않는데도(F42·F43 제외) 기록·가시화·기본값만으로 두 플레이어의 보수를 바꿈. 관측 모드 안에서 가능한 최대치
검증 가능성모든 확률에 나중 결과가 붙어 브라이어 점수로 검증됨. "에이전트를 의심하는 근거"가 감이 아니라 숫자가 됨
